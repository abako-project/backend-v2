## R1 accepted

Added explicit project-content and worker-directory copy tables through additive,
idempotent migration 0014. Payloads contain descriptive content, task presentation
and identity/revision context, not balances, escrow or lifecycle authority.
Fingerprints select the exact provider-derived content version; concurrent older
and newer reads cannot overwrite a current-pointer row. Scope includes generation
and entity ID. Copies are compared against the provider source before composition;
corrupt or mismatched copies fail explicitly. This is not an onchain commitment.

Visible Project/list and standalone task reads compose from these verified copies;
worker directory reads use copied names, distinct from mutable principal/profile
names. Project visibility is checked first. Raw authorization and financial reads
remain provider-based. Large Project copying/encoding/decoding runs on the existing
blocking pool. The provider remains the only authoritative writer in R1.

Reads backfill their selected content idempotently. For complete backfill, the
same adapter binary accepts:

```sh
adapter-api backfill-provider-content
```

It uses normal adapter configuration, reads one bounded owner-provided snapshot
over HTTP, writes/verifies copies serially, logs only counts and exits. It neither
reads the provider database nor signs/submits operations. Partial backfill is safe
to retry. No such command was run against a live deployment.

## R2 preflight and predecessor bridge (accepted)

Astra xhigh recommends R2a worker names + Project title/description first, with
proposal and catalog changes reviewed separately as R2b. Use explicit WorkerCore,
ProjectCore and CoreSnapshotV2 private protocol types in generated-contracts;
public REST DTOs stay unchanged. R2a can retain unchanged proposal/task children.
Do not construct provider public views with empty substitute strings or hide
content flags in public DTO codecs. Raw core facts still serve auth/visibility,
command resolution, briefs/reviews/participants and private channels; hydrate only
requested presentation after filtering. Native/WASM comparison moves to complete
core facts, metadata refs and shell history, with API tests for presentation.

New Project IDs remain generated by the captured RNG during execution. Bind its
staged record to generation + creator + existing operation ID and associate the
returned Project ID after confirmation; consume no extra RNG. Immutable name/
Project text records need no new editing API or revision mechanism.

Rollback requires a predecessor decoder/replay build: Shell validates every
retained call's bytes, so a rehydrated old archive containing newly appended
commands cannot be loaded by the unmodified R1 binary. The bridge adds only wire
recognition/replay, not a second legacy business engine. Preserve all exact
accepted bytes/receipts; reject unsupported fresh work only after replay
admission. Reconcile pending/unknown work in both directions. Actual rollback
after successful new core writes remains a required R2a gate, not established by
this preparatory bridge test alone.

Accepted bridge scope: private MetadataCommitmentV1 and worker-core
registration input; appended command indexes49/50; operation identity binding;
native fresh-execution gate before any business effect. Public routes still send
their current commands. Focused tests cover unchanged legacy indexes, new wire
round trips, metadata operation mismatch rejection, fresh compact failure with
unchanged state, SQLite import/reopen/replay of simulated successor rejection
history and further ordinary work. The equivalent sandbox import/replay test
also passes. This fixture simulates a valid successor domain rejection; no new
core business handler is enabled or claimed implemented.
